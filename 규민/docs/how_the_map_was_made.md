## 용어 (처음 나오는 순서)

- OSM(OpenStreetMap): 누구나 편집하는 공개 지도. 점(node), 선(way), 묶음(relation)으로 이뤄진다
- way: 점을 이은 선 하나. 도로 한 구간. 종류는 highway 태그에 적는다
  (예: residential 주거지 도로, unclassified 등급 없는 일반 도로, service 부속 도로, footway 보도)
- 태그(tag): way 에 붙은 "키=값" 속성. highway=service, service=parking_aisle(주차장 안 통로) 같은 것
- changeset: OSM 편집 한 묶음의 번호. 누가 언제 무엇을 고쳤는지 남는다
- OpenDRIVE(xodr): 자율주행 시뮬레이터가 읽는 도로 지도 표준 형식(XML). 도로 중심선 모양과 차선 구성을 적는다
- road: xodr 의 도로 한 조각. 기준선 하나와 그 옆 차선들로 이뤄진다
- 기준선(reference line): road 의 차선 위치를 재는 기준 선. 이 맵에서는 곧 중앙선
- lane(차선): 기준선에서 옆으로 몇 m 떨어진 띠. 번호가 음수면 진행 방향 오른쪽, 양수면 왼쪽
- junction(교차로): 도로가 만나는 곳. 안에 커넥터들이 들어 있다
- 커넥터(connecting road): junction 안에서 들어오는 road 와 나가는 road 를 잇는 짧은 road. 좌회전·직진·U턴마다 하나씩
- paramPoly3: xodr 이 곡선 모양을 적는 방식. 3차 다항식 곡선 조각을 이어 붙인다. 조각 이음매에서 곡률이 튄다
- Osm2Odr: CARLA 가 제공하는 OSM -> OpenDRIVE 변환기(carla.Osm2Odr.convert)
- SUMO / netconvert: SUMO 는 교통 시뮬레이터, netconvert 는 그 도로망 변환 도구. Osm2Odr 는 이것을 안에 품고 있다
- 투영(projection): 둥근 지구의 위도·경도를 평면 x, y(미터)로 펴는 계산
- TM(횡메르카토르, Transverse Mercator): 투영 방식 하나. 기준 경선(중앙자오선, lon_0) 근처만 정확하다
- 메시(mesh): CARLA 가 xodr 을 읽고 만드는 3D 도로 표면(삼각형 모음). 차는 이 메시 위를 달린다
- spawn point: 차를 놓을 수 있는 위치 후보. CARLA 가 도로에서 자동으로 뽑는다

## 2. 왜 그대로는 안 됐나

무엇
- 캠퍼스 안 차도가 OSM 에서 거의 전부 highway=service + service=parking_aisle(주차장 안 통로)로 적혀 있었다
- Osm2Odr 의 기본 변환 대상 도로 종류에 service 가 없다. 그래서 그대로 넣으면 캠퍼스 도로가 통째로 빠진다
  - 기본 목록(CARLA 0.9.15 공식 문서): motorway, motorway_link, trunk, trunk_link, primary, primary_link,
    secondary, secondary_link, tertiary, tertiary_link, unclassified, residential
  - 실제 증거: 지금 xodr 파일 머리말에 변환기 설정이 그대로 남아 있다.
    keep-edges.by-type = 위 12개 종류. service, footway, track 없음 (s22 재확인)
  - 보정 없이 내부+경계만 변환하면 "No edges loaded" 로 변환 자체가 실패했다(세션1 실측)

누가 그렇게 적었나 (s22 재확인, 원본 OSM 의 way 속성)
- changeset 129142899, 2022-11-20, 편집자 표기 user_17703046
  - OSM 은 탈퇴한 계정을 "user_<번호>" 로 표시한다. 그래서 "계정 삭제됨" 이다. 작성자에게 물어볼 수 없다
  - 지금 기준 약 3년 10개월 전(지시문 "4년 전" 은 반올림)
- 이 changeset 이 마지막으로 고친 way 312개 중 236개가 service=parking_aisle.
  OSM 전체 parking_aisle 425개 중 236개가 이 한 번의 편집에서 나왔다
- 우리가 보정한 73개 중 66개가 이 changeset 이 마지막으로 고친 way 다
- 주의(사실 구분): 이 편집이 의도적으로 잘못 적었는지는 알 수 없다. 사실은 "교내 주행 도로가 주차장 통로로 분류돼 있다" 이다

왜 문제인가
- service 를 빼는 것은 변환기 쪽 설계로는 합리적이다(주차장 통로까지 도로로 만들면 지도가 지저분해진다).
  문제는 데이터 쪽이다. 캠퍼스 간선이 주차장 통로로 적혀 있어 정상 도로가 함께 버려진다

결과
- 태그를 고치지 않으면 캠퍼스 도로망을 만들 수 없다 -> 3단계(태그 보정)가 "정리" 가 아니라 필수 단계가 됨

그림 2 구조: 같은 캠퍼스 지도를 두 장. 왼쪽 "OSM 에 있는 길"(service 를 회색으로 많이), 오른쪽 "변환기가 받아들이는 길"(거의 빈 지도)

교수님이 물으면
- "OSM 을 직접 고쳐 올리면 되지 않나" -> 공개 지도 원본은 고치지 않았다. 우리 사본에서만 바꿨다(원본 파일 sha256 불변).
  공용 데이터를 실측 없이 바꾸는 것은 범위 밖이다
- "변환기의 도로 종류 목록에 service 를 넣으면 되지 않나" -> 가능하다(set_osm_way_types). 그러나 그러면
  변환 입력(485 way) 안의 service 219개(내부 195 + 경계 24)가 전부 들어와 주차장 통로까지 도로가 된다. 필요한 way 만 골라 태그를 바꾸는 쪽을 택했다

(osm_survey.md "CARLA Osm2Odr 변환 기본 동작", "2-2 검증 후 road 출처 분해", xodr 머리말)

## 3. 태그 보정 (73개 way 를 unclassified 로)

무엇
- 고른 way 의 highway 값만 unclassified 로 바꿨다. 다른 태그(oneway, service 등)는 그대로 둔다
- 73개 = 처음 19개 + 추가 채택 54개
- 바꾸기 전 종류(s22 재확인): service=parking_aisle 64, footway 6, path 2, track 1

어떤 기준으로 골랐나 (세 갈래)
1. 길이 기준 16개 (세션1): 길이 200m 이상 AND 양 끝이 각각 다른 길 2개 이상과 이어짐(막다른 길 아님) AND 캠퍼스 안/경계.
   = 간선 후보. 알려진 간선 2개(446440340, 774924319)가 다 걸러져 나와 기준이 맞다고 봤다

## 4. OSM -> OpenDRIVE 변환

무엇
- osm_to_xodr.py 가 carla.Osm2Odr.convert(osm 문자열, 설정) 한 번 호출. CARLA 서버 없이 파이썬 라이브러리로 된다
- Osm2Odr 의 속은 SUMO 의 netconvert 다
  - 근거 1: CARLA 0.9.15 빌드 스크립트(Util/BuildTools/BuildOSM2ODR.sh)가 carla-simulator/sumo 포크의
    고정 커밋 1835e1e9 를 받아 빌드한다(세션4 원문 확인)
  - 근거 2: 만들어진 xodr 맨 위 주석에 netconvert 설정 파일이 통째로 들어 있다 (s22 재확인)
    geometry.remove, roundabouts.guess, edges.join, junctions.join, sidewalks.guess, osm.sidewalks, osm.crossings,
    default.lanewidth 3.35, default.sidewalk-width 2.80, keep-edges.by-type(2단계의 12개 종류)
  - 그래서 "OSM 을 SUMO 도로망으로 읽고 -> SUMO 가 OpenDRIVE 로 내보낸다" 는 두 단계다.
    인도 생성, 교차로 묶기, 커넥터 모양은 전부 netconvert 가 정한다

설정 11개 (carla.Osm2OdrSettings, 설치판에서 dir() 로 센 공개 항목. 값 9 + 메서드 2) (s22 재확인)
- default_lane_width = 3.35 (바꿈 아님, 명시) — 설치판 실제 기본값. 공식 문서는 4.0 이라 적었지만 실측은 3.35

## 5. 투영 문제 — 지도가 1.30배 커졌던 이유

무엇 (증상)
- 첫 변환 지도(세션1~2)는 실제보다 약 1.30배 컸다
- 측정: 원본 OSM 점 위치를 그대로 아는 junction 25개, 5m 이상 떨어진 300쌍의 거리를 비교.
  실제 거리는 위경도에서 구면 공식(haversine)으로, 지도 거리는 xodr 좌표로
  - 평균 1.2987, 먼 쌍(589m 이상) 1.2974 ± 0.0050 으로 수렴
  - 방향 8구간 모두 1.296~1.310 = 방향에 상관없이 똑같이 커짐(등방)

원인
- xodr 머리말의 투영식이 "+proj=tmerc" 한 줄뿐이었다. 중앙자오선(lon_0)이 빠져 있었다
- 투영 라이브러리(PROJ) 공식 문서: lon_0 의 기본값은 0.0 = 영국 그리니치
- TM 은 중앙자오선에서 멀어질수록 배율이 커진다. 캠퍼스는 동경 127.46° = 중앙자오선에서 127° 떨어져 있다(정상 사용 범위를 크게 벗어남)
- 검산 1 (배율 이론값, s22 계산): 구면 TM 의 배율 k = 1/√(1−B²), B = cos(위도)·sin(경도차)
  = cos 36.63° x sin 127.46° = 0.637 -> k = 1.297. 실측 1.2974 와 맞다
- 검산 2 (세션3): 같은 식으로 캠퍼스 중심의 투영 x 를 계산하면 4,798,744m, 실제 offset.x 는 4,809,508m(차이 0.22%).
  "좌표가 수백만 m 로 튀었다가 offset 으로 되돌려졌다" 는 물증
- 배제한 설명: "위경도->미터 환산식의 cos 근사 오차" — 그렇다면 동서 방향만 틀어져야 하는데 방향 무관이었다

왜 그냥 1.3 으로 나눠 쓰지 않았나
- 거리·시간은 나누면 되지만 차선 폭은 안 된다. 3.35m 로 적은 차선이 실제로는 3.35/1.297 = 2.58m 크기로 그려진다.
  차는 실제 크기라 지도와 맞지 않는다
- 모든 분석 스크립트가 배율을 기억해야 하면 하나만 빠뜨려도 결과가 조용히 틀린다

해결
- 캠퍼스 중심을 중앙자오선으로 둔 지역 TM 을 지정
  +proj=tmerc +lat_0=36.627298 +lon_0=127.456394 +ellps=WGS84
  (중심 = 보정점 25개 평균. 1km 떨어진 곳 배율 오차가 이론상 1억분의 1 수준)
- 국가 표준(UTM 52N, 중앙자오선 129°)도 검토했으나 캠퍼스가 1.5° 떨어져 1km 당 약 20cm 오차가 남아 지역 TM 을 택함.
  Autoware 도 결국 지도 원점을 위경도로 따로 지정하므로(map_projector_info) 손해가 없다
- 결과: 같은 300쌍 비율 1.2987 -> 0.9997(± 0.0048). 지금 맵(73개판)은 OSM 점 90개로 다시 맞추면 배율 1.000709, 회전 0.065°, 잔차 3.7m

이것이 "왜 지도가 커졌나" 의 답이다
- 한 줄: 투영식에 기준 경도가 빠져 지구 반대편(그리니치) 기준으로 펴졌고, 거기서 127° 떨어진 한국은 1.3배로 늘어났다.
  기준 경도를 캠퍼스 중심으로 지정해 1.000 으로 고쳤다

그림 5 구조: 지구본에 세로선 두 개. 그리니치(0°)와 캠퍼스(127.46°). 두 경우 "펼친 종이" 위 캠퍼스 크기 비교(1.3배 / 1.0배)

교수님이 물으면
- "왜 처음에 기준 경도가 없었나" -> 변환기 기본 투영식이 "+proj=tmerc" 하나뿐이다(설정을 안 바꾸면 항상 이 값, 변환 로그 확인)
- "proj.db 경고는?" -> 여전히 나온다. 그러나 결과 축척을 실측(0.9997)으로 확인했으므로 결과에는 영향이 없다고 판단

## 6. 반쪽 도로 구조 — 뒤에 나오는 문제들의 공통 원인

무엇
- 이 맵의 road 878개는 전부 "한 방향 차선 1개(+인도)" 만 가진다. 왼쪽 차선이 하나도 없다
  - 504개: 주행 차선(lane -1, 3.35m) + 인도(lane -2, 2.80m). 374개: 주행 차선만
- 실제 양방향 길 하나가 서로 반대 방향인 road 두 개로 쪼개져 있다
  - 일반 road(교차로 밖) 260개 중 240개가 이런 쌍. 쌍의 기준선은 정확히 겹치고(이격 0.000m) 방향만 180° 반대
  - 예: road1247(정문 진입) <-> road1120
- 그래서 878 road 가 전부 일방통행이다. 경로는 반드시 방향 그래프로 뽑아야 한다

왜 이렇게 됐나
- netconvert(SUMO)의 도로 조각(edge)은 한 방향 단위다. 양방향 길은 edge 두 개가 되고, OpenDRIVE 로 쓸 때 edge 하나가 road 하나가 된다
  (SUMO 구조에서 나온 설명. 이 프로젝트에서 소스 줄 단위로 확인하지는 않았다)

뒤에 나올 문제와의 연결 (이 단계를 이해하면 나머지가 풀린다)
1. 1m 벽(8단계): 벽은 road 의 가장 바깥 차선 가장자리에 선다. 왼쪽 차선이 없으니 "왼쪽 가장자리" = 기준선 = 중앙선
2. 곡선 접힘(9단계): 좌회전이든 우회전이든 쌍 중 한쪽 road 의 인도가 커브 안쪽에 온다
3. U턴 커넥터: 교차로마다 반대편 쌍둥이로 넘어가는 U턴 커넥터가 생긴다(U턴형 143개). 직진 커넥터와 겹쳐 있어
   세션13 에 CARLA 기본 자동주행(TM)이 직진 대신 U턴 커넥터(r1697)를 골라 인도로 올라갔다 -> BasicAgent(경로 추종기)로 전환
4. 막다른 끝 회차: 길 끝마다 길이 9.89m, 평균 반경 4.47m 의 같은 틀 커넥터가 붙는다(netconvert 의 템플릿 곡선)

## 7. CARLA 가 xodr 을 불러오는 방법 (로드 파라미터)

무엇
- CARLA 서버에 xodr 문자열을 보내면(client.generate_opendrive_world) 서버가 도로 3D 메시를 그 자리에서 만든다
- 이때 메시 모양을 정하는 값이 carla.OpendriveGenerationParameters 7개다. xodr 파일 안에는 이 값이 없다
- 명령: python map/tests/test_load_map_878.py --wall-height 0 (7개 전부 인자로 바꿀 수 있게 만듦, 세션12)

7개 값 (CARLA 0.9.15 공식 Python API 문서 기본값 = 우리 값, wall_height 만 다름)
- vertex_distance = 2.0m: 메시 점을 도로를 따라 2m 마다 찍는다. 곡선은 2m 짜리 직선 조각들로 근사된다
  -> 9단계 지표(R2)가 2m 창을 쓰는 이유
- max_road_length = 50m: 메시 한 덩어리의 최대 길이. 긴 road 는 50m 단위로 나눠 만든다
- additional_width = 0.6m: junction 안 차선을 메시로 만들 때 더하는 폭(교차로 메시 사이 틈을 막는 여유)
- smooth_junctions = True: junction 메시를 부드럽게 다듬는다
- wall_height = 1.0m(기본) -> 0.0 으로 바꿈. 도로 가장자리 안전 벽 높이. 8단계
- enable_mesh_visibility = True: 도로 메시를 화면에 그린다
- enable_pedestrian_navigation = True: 인도 위 보행자 길찾기 정보를 만든다

왜 6개는 기본값인가
- 바꿀 근거가 없었다. 한 번에 하나만 바꾸는 원칙(벽 하나만 바꿔 대조 실험)

결과
- road 878 / junction 95 / spawn point 1243. 서버가 받은 지도 문자열(to_opendrive)의 sha256 이 파일과 바이트 단위로 같음(세션20 확인)

그림 7 구조: xodr(선과 숫자) -> [서버: 2m 간격 점 찍기 -> 삼각형 메시 -> 가장자리에 벽 세우기] -> 3D 도로

교수님이 물으면
- "왜 지도 파일이 아니라 로드 단계에서 벽을 끄나" -> 벽은 지도에 없고 로드 때 만들어진다. 그래서 같은 파일로 벽만 켜고 끌 수 있었다(8단계 대조 실험)

## 8. 1m 벽 문제

무엇 (증상)
- 차가 정문 앞 커브(road1247 s≈92m, 세션7~10)와 548m 지점(road1240 끝, 세션12)에서 계속 멈췄다
- 멈출 때 가속 페달 0.85, 브레이크 0 = 차가 스스로 선 것이 아니라 무언가에 걸렸다. 충돌 센서: 세션10 1,604건, 세션12 2,139건

원인
- CARLA 는 메시를 만들 때 도로 "가장 바깥 차선의 가장자리" 에 높이 1m 벽을 세운다. 도로 밖 빈 공간으로 차가 떨어지지 않게 하는 마지막 안전 장치다
- 반쪽 도로(6단계)는 왼쪽 차선이 없다 -> 왼쪽 가장자리 = 기준선 = 중앙선 -> 왼쪽 벽이 중앙선 위에 선다.
  쌍둥이 road 도 같은 선에 벽을 세운다 -> 양방향 길 한가운데 1m 벽
- 커브에서 차가 조금만 중앙선 쪽으로 붙어도 벽에 걸린다

확인 방법 (서로 독립인 세 가지)
1. 소스 대조: CARLA 0.9.15 공식 GitHub MeshFactory.cpp. junction 이 아닌 road 에만, 가장 오른쪽 차선의 오른쪽 가장자리와
   가장 왼쪽 차선의 왼쪽 가장자리에, 높이 벡터 (0,0,wall_height) 만 더한 수직면을 만든다
2. 화면 높이 측정: 세션12 정지 지점 옆 스크린샷에서 수직 판의 위·아래 픽셀로 거리와 높이를 함께 풀었다(핀홀 카메라 모델).
   0.94~1.08m = 1m (figures/16, 17)
3. 충격량 방향: 위아래 성분이 거의 없다 = 수평으로 미는 수직면
   - 세션10(92m): 1,604건 전부 차를 오른쪽으로 밀었다 = 접촉면은 차의 왼쪽(중앙선 쪽). 차 왼쪽 모서리가 기준선을 0.19m 넘은 뒤 멈춤
   - 세션12(548m): 2,138건이 차를 왼쪽·앞으로 밀었다(위아래 성분은 크기 대비 0.008 이하). 소스 규칙대로 벽 선을 다시 그리면
     road1240 끝에서 끝나는 중앙선 벽의 끝점이 첫 충돌 순간 차 앞부분 bbox 안(앞 왼쪽 모서리에서 0.25m)에 들어와 있었다.
     좌회전을 일찍 시작해 앞머리가 중앙선을 넘은 뒤, 끝난 벽 끝이 차 앞부분 오른쪽에 낀 모양으로 설명된다(추정)
   - 두 경우 방향은 반대지만 둘 다 "중앙선 위 벽" 으로 설명되고, 다른 후보(바깥 벽)는 3.65m 이상 떨어져 있었다

대조 실험 (같은 파일, 벽만 바꿈)
- 벽은 xodr 안에 없다(파일 안 "wall" 0건). 로드 파라미터다
- 그래서 같은 xodr(sha256 bf835cdfad0cea65), 같은 주행 스크립트로 wall_height 1.0 / 0.0 만 바꿨다
  - 세션12 벽 1.0: 548m 에서 정지, 충돌 2,139건
  - 세션13 벽 0.0: 충돌 0건, 554m 까지 진행(그 뒤 실패는 벽이 아니라 TM 의 U턴 커넥터 선택 = 6단계 3번)
- 같은 위치·각도 스크린샷에서 수직 판이 사라진 것도 확인(figures/18, 19)
- 이후 모든 주행(세션13~21) 충돌 0

수치 정정 (지시문 "1604건 -> 0건")
- 1,604건은 세션10, 곡선 평활화(9단계) 전 파일의 92m 정지다. 같은 파일 대조 실험의 수치는 2,139 -> 0 이다

## 9. 급커브 평활화 (필렛)

무엇 (증상)
- OSM 의 길은 점을 직선으로 이은 꺾은선이다. 변환기가 그 꺾인 모서리를 아주 작은 반경의 곡선으로 만든다
- 반쪽 도로라 커브 안쪽에는 쌍둥이 road 의 인도가 온다. 기준선에서 인도 바깥 끝까지 6.15m(차선 3.35 + 인도 2.80)
- 커브 반경이 6.15m 보다 작으면 안쪽 인도 가장자리 선이 자기 자신과 겹쳐 접힌다(메시가 쐐기처럼 꼬임)

임계값과 근거
- 접힘 계수 f = 1 − (6.15 / R). f ≤ 0 이면 접힘. 6.15m 는 차 성능이 아니라 차선+인도 폭에서 나온 기하 한계다
  (지시문의 "물리 최소 6.15m" = 이 기하 한계)
- 수용 기준 f ≥ 0.30 <=> R2 ≥ 6.15/0.70 = 8.79m
  - 뜻: 메시 점 간격이 2m 일 때 안쪽 인도 바깥 점 간격이 0.6m 이상 남는다. 공학적 선택값이다(CARLA 에서 유도한 값 아님)
- 필렛 목표 반경 R_T = 11.0m, 받아들이는 하한 R_ACC = 10.0m
  - 변환기를 거치면 반경이 줄어든다(실제 경로 커브에서 0.91~0.95배). 8.79/0.91 = 9.7 -> 하한 10.0
  - 11.0m 여유 내역: 11.0 − 6.15 = 4.85m = 접힘 경계에서 수용 기준까지 2.64 + 변환기 손실 0.9 + 헤드룸 1.3
  - 스윕: 10~12m 는 남는 문제 지점 수가 거의 같고, 11 에서 경로 핵심 두 커브가 f 0.42/0.40. 14m 이상은 이웃 점과 너무 가까워 필렛이 성립 안 함

방법
- 문제 꼭짓점을 반경 R 원호로 깎는다(fillet). 접선 길이 T = R·tan(θ/2), 호 위에 2m 간격 점 삽입
- 원래 선에서 2m 넘게 벗어나는 필렛은 하지 않는다(실제 도로 위치를 지키려고). 이웃 필렛과 겹치면 R 을 줄이고, 10m 미만이 되면 건너뜀
- 고친 곳은 OSM 단계(점 추가)다. xodr 을 직접 고치지 않고 다시 변환한다 -> 변환기가 연결 관계를 일관되게 다시 만든다
- 대상은 "변환 -> xodr 에서 측정 -> 문제 꼭짓점만 필렛 -> 재변환 -> 재측정" 으로 고른다.
  꺾임 각도로 고르면 안 된다(10° 이상 꼭짓점 492개 중 실제 원인은 71개, 14%)

결과

## 부록 A. 커브를 재는 지표 — 무엇을 쓰고 무엇을 버렸나

세 가지 다른 반경이 있다. 이름이 비슷해 섞이기 쉽다
1. 해석적 순간 반경: xodr 곡선식(paramPoly3)을 미분해서 한 점의 곡률로 잰 반경
2. R2 (2m 창 평균 반경): s−1m 와 s+1m 의 진행 방향 차이를 2m 로 나눈 평균 곡률의 역수. R2min = 한 road 안 R2 의 최솟값
3. 평균R: road 길이 / 전체 회전각(라디안). 커브 전체의 평균 반경

왜 R2(2m 창)를 쓰나
- CARLA 는 메시를 2m 간격(vertex_distance 2.0)으로 만든다. 차가 실제로 달리는 면은 2m 조각의 이음이다
- 그러니 2m 보다 짧은 곡률 변화는 메시에 나타나지 않는다. 지표도 같은 해상도로 잰다
- 검증: 필렛 반경(11m)과 변환 후 R2 가 1% 이내로 일치(세션11)

왜 해석적 순간 반경을 버렸나 (세션11)
- paramPoly3 조각 이음매마다 곡률이 튄다(변환기가 만든 스파이크). 해석적 최소 반경이 실제 원호 반경의 약 0.375배로 나온다
- 같은 커브를 평활화한 뒤에도 해석값은 4.06/4.52m 에 머무는데 R2 는 10.59/10.32m. 스파이크는 메시에 반영되지 않는다

R2min 도 통과 여부를 예측하지 못했다 (세션20 주행, 세션21 정리)
- 세션18 은 중문 루트 road1286 의 R2min 1.29m(s=9.5)를 r1592(R2min 5.02m)보다 나쁜 새 위험으로 봤다
- 결과: r1286 통과. 이탈은 인도 쪽 차체 0.84m 로 r1592(1.19m)보다 작았다
- 이유: 2m 길이의 급한 점 하나는 차가 그냥 지나간다. 차의 궤적은 커브 전체를 따라 정해진다
- 이탈량에 더 가까운 것은 평균R(r1286 10.33m, r1592 7.82m)과 진입 속도다
  (r1592 7.82m·19.4km/h -> 1.19m, r1838 5.73m·16.4km/h -> 0.84m)
- 평균R 도 통과/실패 경계는 아니다. 세션18 의 "약 9m 경계" 는 옛 판정 기준에서 나온 값이고 세션20 에 7.82m·5.73m 도 통과했다

용어 정정 (세션21 에서 이미 정리, 이번 지시문에도 반복됨)
- 지시문 1-3 의 "순간 최소 반경은 왜 예측력이 없는가 (r1286 R2min 1.29m 가 통과함)" 는 두 개념이 섞였다
  - 순간(해석적) 반경이 부적합한 이유 = 이음매 스파이크(세션11)
  - R2min 이 예측력이 없던 사례 = r1286 (세션20). R2min 은 2m 창 지표의 최솟값이지 순간값이 아니다
- 정리: R2 는 "메시 접힘(인도 형상)" 판정용 지표로 맞고, "차가 지나갈 수 있나" 예측에는 평균R + 진입 속도가 더 가깝다

교수님이 "반경을 왜 이렇게 여러 개 쓰나" 라고 물으면
- 용도가 다르다. R2 는 도로 메시가 깨지는지(지도 품질), 평균R 은 차가 얼마나 벗어나는지(주행). 순간 반경은 변환기 스파이크 때문에 둘 다에 못 쓴다
