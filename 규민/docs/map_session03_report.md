### A-3. 회전각 -141.89°의 의미

R 행렬을 xodr 방향벡터에 직접 적용해 나침반 방위각으로 환산
(스크립트로 계산, 수기 계산 아님):

| xodr 방향 | 의미 | 나침반 방위각 |
|---|---|---|
| +Y | 그림(01/02/03 png)의 "위쪽" | 약 142° (남동, SE 쪽) |
| -Y | 그림의 "아래쪽" | 약 322° (북서, NW 쪽) |
| +X | 그림의 "오른쪽" | 약 232° (남서, SW 쪽) |
| -X | 그림의 "왼쪽" | 약 52° (북동, NE 쪽) |

즉 어제 그린 평면도(01_full_network.png 등)의 "위쪽"은 진북이
아니라 **대략 남동쪽**을 향한다.

공식 종합안내도와 비교: 지시서에 "북쪽이 좌상단"이라 했으므로,
안내도의 "위쪽"은 정성적으로 대략 북동쪽에 가까울 것으로 추정됨
(좌상단에 북이 있다 → 북에서 시계방향으로 약간 돌리면 위쪽이 됨).
이는 안내도 자체를 보고 정확한 각도를 다시 확인해야 하는
정성적 추정이며, 오늘 계산한 xodr 142°(SE)와는 **약 90도
어긋난다**(직교에 가까움) — 완전히 뒤집힌(180°) 것도, 같은
방향도 아님. 두 도면을 그대로 겹쳐 비교하면 안 되고, 회전
보정이 필요하다는 뜻.

정문/중문/동문/남문의 구체 위치(남동/남/북서/북동)와 junction1/11의
실제 대응 관계는 OSM에 게이트 태그가 없어 이 스크립트만으로는
판정 불가 — 사용자가 위경도로 직접 확인한 뒤 알려주면 대조하겠음.

### A-3 재검토 (사용자 확인 3건, 2026-09-17)

사용자가 정문(제1문) 위치를 OSM에서 직접 확인 
(36.631513, 127.453602 = 정문 안쪽, 법학전문대학원 N2 옆).
확정: 빨간 구간 아래끝(junction1)=정문, 위끝(junction11)=중앙도서관
방향. plot 아래→위 = 실제 북서→남동.

**검산 1 — θ=-141.89°와 bearing=142°의 관계**
- θ(피팅 결과)는 R행렬의 회전각. (x,y)=(east,north)를 "표준수학각"
  (+X=east 기준 반시계)으로 다루는 값
- bearing(나침반방위각)은 "+Y=north 기준 시계"로 다루는 값 →
  같은 (east,north)를 다른 기준으로 읽은 것이라 정의부터 다름
- xodr +Y축의 mathangle은 정확히 90°이므로
  bearing(+Y) = 90 - mathangle(회전후) = 90 - (90+θ) = **-θ**
- 그래서 +Y축만 놓고 보면 "부호반대·크기같음"이 정확히 성립
  (우연 아니라 항등식). 근거: bearing_of_xodr_vector() 직접계산,
  +X축은 mathangle=0이라 이 항등식이 깨짐(θ=-141.89 그대로
  이동하여 bearing(+X)=231.89, "-θ"와 다름) → +Y축에만 적용되는
  관계임을 확인

**검산 2 — 공식안내도 "위쪽=북동" 근거 재확인**
- 원래 표현이 부정확했음. 정정: 안내도의 나침반 표시(N)가
  좌상단(대각선) 방향을 가리킨다는 지시서 문장을 가정("정확히
  45° 대각선")하여 벡터로 직접 계산한 결과이지, 안내도 자체에서
  "위쪽"이 직접 북동이라 쓰여있는 게 아님
- 계산: N방향 화면벡터=(-1,1)/√2(좌상단) → world=Rot(α)*screen
  풀면 α=-45° → 화면"위쪽"(0,1)의 world 방향=(E,N)=(.707,.707)
  = 나침반 45°(북동) — 스크립트로 검산 완료(수기 아님)
- 이 결론은 "N 표시가 정확히 45° 대각선"이라는 가정에 의존하는
  근사치. 실제 안내도의 N 각도가 다르면 값도 달라짐 — 사용자가
  안내도 원본에서 정확한 각도(또는 최소 사분면)를 확인해주면
  가정을 대체하겠음. 현재로선 "확정"이 아니라 "추정"

**검산 3 — junction1→junction11 실측 검산**
- β_true(구면 초기방위각 공식, lat/lon만 사용, 변환 파이프라인
  미사용): 125.7550°
- α_plot(그림 내 각도, xodr Δ만 사용: 그림 위쪽=0·시계방향):
  343.1289°
- β_true - α_plot = 142.6261°
- 검산1에서 유도한 -θ = 141.8948° 와 비교 → **오차 0.7313°로
  일치**(이 두 점의 피팅 잔차 5.253m/2.482m, 두 점 간 실거리
  389.6m 대비 각도오차로 환산하면 0.7~0.8° 수준과 부합, 별도
  이상 없음)
- 결론: 방위 해석(회전각→나침반각 변환식, "+Y=대략 남동")은
  독립적인 실측 검산으로 확정. 검산2(공식안내도 비교)만 추정 단계

## Phase B — 스케일 0.7716 규명

### B-1. 스케일 방향

fit_similarity()의 정의: dst(실제ENU,m) ≈ s · R · src(xodr) + t
→ **s=0.771623 는 "xodr → 실제" 방향** (xodr좌표에 곱하면 실제
미터가 나옴). 역으로 "실제 → xodr"는 1/s=1.2960배.

**결론: xodr이 실제보다 크다.** xodr상 거리는 실제 거리의 약
1.296~1.298배(뒤 B-2 실측 참고) — 실제보다 약 **29.6~29.8% 부풀려짐**.

### B-2. 직접 측정 (적합 결과 재사용 없음)

방법: junction 25개(전부 원본OSM 노드ID 직접매칭, 오차0) 중
5m 이상 떨어진 300개 쌍 전수 계산.
- 실제거리: **구면 haversine 공식**(위경도만 사용, geo_calibrate.py의
  111320/cos 근사·R·s·t 전부 미사용 — fit_similarity 호출 안 함)
- xodr거리: 원본 xodr x,y 유클리드 거리(R 미적용, 원좌표 그대로)
- 비율 = xodr거리/실제거리

결과(map/scripts 직접 실행, 재현가능):
- 전체 300쌍: 평균 1.2987, 표준편차 0.0247, 범위 1.1818~1.6484
- 거리별: 짧은쌍(12~385m) 평균1.3008/표준편차0.0415 →
  중간쌍(385~588m) 1.2979/0.0084 → 먼쌍(589~1097m) 1.2974/0.0050
  **거리가 멀수록 표준편차가 급감하며 ~1.297로 수렴**
  (단거리 변동은 OSM 노드 좌표 자체의 위치 정밀도 잡음으로 판단 —
  절대오차가 같아도 짧은 분모에서는 비율 흔들림이 커짐)
- 방위각별(45도 8구간, 짧은거리 필터 없이 전체): 전 구간
  1.2957~1.3101 — **방향에 따른 체계적 차이 없음(등방)**

**일정성 판정: 균일(등방).** 위치·방향 의존 왜곡의 흔적 없음.
장거리 쌍만 보면 사실상 상수(1.296~1.298).

### B-3. 원인 판정

**xodr 헤더 원문**: `<geoReference><![CDATA[+proj=tmerc]]></geoReference>`
`<offset x="-4809508.84" y="-14375579.01" z="0.00"/>`

**(a) 투영 문제 — 채택**
- PROJ 공식문서(proj.org, tmerc 페이지, 2026-09-17 조회) 원문 인용:
  "+lon_0 ... Defaults to 0.0." — geoReference에 lon_0이 없으므로
  중앙자오선=0°(그리니치)로 투영됐다는 것이 공식문서로 확정
- 캠퍼스는 동경127.45° → 중앙자오선에서 127.45° 떨어짐(TM 정상
  사용범위 ±90°를 훌쩍 넘음)
- 검증: 구면 TM 근사식(B=cosφ·sinΔλ, x=R/2·ln((1+B)/(1-B)))으로
  캠퍼스 중심 위경도를 직접 계산 → 예상 |x|=4,798,744m,
  실제 offset.x=4,809,508.84m, **차이 0.22%** — 소구경 구면근사임을
  감안하면 사실상 일치. offset이 "빼서 원점 근처로 되돌리는" 값임을
  감안하면, 애초에 투영 결과가 수백만m로 튀었다는 물증
- B-2에서 확인한 "등방성"도 부합: TM은 등각(conformal)투영이라
  국소적으로 방향 무관 배율을 가짐 — 이번처럼 좁은 지역(약
  1.7km)에서 등방적 배율로 나타나는 것과 일치

**(b) 위경도→미터 환산 근사 오차 — 배제**
- cos(36.62°) = 0.802609, 측정된 s=0.771623 → 비율 0.9614
  (약 3.9% 차이, 깔끔히 맞아떨어지지 않음). cos제곱(0.6442)과도
  안 맞음(비율 1.198) — **숫자로 대조한 결과 우연한 근접일 뿐,
  정확한 관계 아님**
- 더 결정적 근거: cos(lat) 근사오차는 **경도(동서) 방향에만**
  영향을 주는 구조(latlon_to_enu의 동쪽 성분에만 cos 곱함) →
  존재한다면 방위각에 따라 비율이 달라져야 함(동서 성분 쭈그러들거나
  늘어나는 이방성). 그러나 B-2에서 8개 방위 구간 전부
  1.296~1.310으로 **방향 무관**이었음 → cos 근사오차라면 나올 수
  없는 패턴
- 게다가 B-2의 "실제거리"는 이 근사식(111320/cos)을 아예 쓰지
  않고 순수 haversine으로 계산했는데도 같은 비율(1.297)이
  나옴 → 스크립트 자체의 근사식은애초에 이 비율의 원인이 될 수
  없음(사용조차 안 됐으므로)
- **결론: (b) 배제.** cos값과 s가 비슷해 보인 것은 우연(둘 다
  대략 0.77~0.80대라는 것 뿐, 관계식 없음)

**(c) 기타 — 불필요**: (a)로 설명력 충분(공식문서 근거+수치일치
+등방성 3개 독립 근거가 모두 부합), 추가 후보 조사 불필요 판단

  충분함. 중앙자오선에 데이터 중심을 두면 반경 1.7km 규모에서
  TM 배율오차는 무시할 수준(수 mm 이내)으로 줄어듦
- **주의(미해결 변수)**: 변환 로그에 `pj_obj_create: Cannot find

  넣어도 내부적으로 완전히 의도대로 처리되는지 불확실. 재변환
  시 반드시 재확인 필요(경고가 그대로 나오는지, 결과 스케일이
  실제로 1.0에 가까워지는지)
- **road/junction id 영향**: 투영은 좌표값 계산 단계이고 도로
  위상(어떤 way가 road/junction이 되는지)은 OSM 태그·연결성 기준
  으로 SUMO netconvert가 먼저 결정하는 별도 단계로 알고 있음 →

  개수(134)·junction 개수(25)·강조구간 id(319/299/404/405/318)가

- **재변환 비용**: 기존 `osm_to_xodr.py`에 `settings.proj_string`
  한 줄 추가만 필요(스크립트 구조 변경 없음). CARLA 서버 불필요,

  실측 아님, 확정값 아님)

### 실용적 판정 — 스케일 오차가 실제 문제가 되는가

**결론: 문제가 된다. 재변환을 권장한다.**

근거 두 갈래:

1. **"환산으로 해결 가능한 부분"과 "안 되는 부분"이 섞여 있음**
   - 등방·균일(B-2 확정)이므로 이동시간·직선거리 같은 값은
     이론적으로 상수 0.7716(또는 1.2960)을 곱해 환산 가능
   - 그러나 **차선 폭은 환산이 안 되는 구조적 문제**: 
     `DEFAULT_LANE_WIDTH=3.35`는 CARLA 런타임 "실측 기본값"으로
     실제 미터 단위를 의도하고 고른 값(osm_to_xodr.py 주석 근거)
     인데, 이 값이 그대로 xodr 단위로 박혀 들어감. 1 xodr단위
     =0.7716 실제m이므로, **실제로 구현된 차선폭은
     3.35×0.7716=2.585m** — 실제 승용차 통행 최소폭에도 못
     미치는 비현실적 좁은 차선. 이건 사후에 숫자만 곱해서
     고칠 수 없음(CARLA 3D 메쉬 자체의 폭이자, 스폰되는 차량은
     실제 크기 모델이라 기하학적으로 안 맞음)
   - 즉 "지표 환산" 전략은 거리·시간류에는 쓸 수 있어도 **차선폭
     같은 절대 기하값에는 원천적으로 안 통함**

2. **환산 전략 자체의 운영 리스크**
   - 이후 실험(이동시간, 정지거리, 속도프로파일 등) 전체에
     "0.7716을 곱하거나 나눠야 한다"는 규칙을 모든 분석 스크립트
     ·보고서에 빠짐없이 적용해야 함 — 한 곳이라도 빠뜨리면
     결과가 조용히 틀어짐(발견하기 어려운 부류의 오류)
   - 반면 재변환은 원인(proj_string)을 소스에서 고치는 것이라
     이후 전부 1.0 배율로 일관되게 맞음 — 유지보수 부담이 훨씬
     낮음

**요약**: 등방성만 보면 "환산 가능"해 보이지만, 차선폭처럼
환산이 통하지 않는 절대 기하값이 이미 하나 확인됐고, 이 프로젝트
평가기준(재현성·안전성)상 매 스크립트마다 배율보정을 기억해야
하는 방식은 재현성 리스크가 큼 → **재변환이 더 안전한 선택**.
단, 재변환 실행은 사용자 승인 후.

### C-1. 정문–중앙도서관 경로

그래프 탐색 방법: road의 predecessor/successor(elementType=road인
링크만 사용해 union-find, junction 슈퍼노드로 뭉개지 않고 실제
connecting road를 그대로 하나의 edge로 포함) + Dijkstra. 시작점=
정문(junction2=OSM 2261340221, road300의 시작), 도착점=중앙도서관
인근(junction11=OSM 4402717742).

**결과: 경로 존재.**
- 총 길이: **539.75m** (재변환본 좌표=실제 미터, 환산 불필요)
- 거친 road: **6개**(일반road 3 + junction connector 3) —
  road300(153.25m, 정문~junction1) → connector402(4.29m,
  junction1) → road319(37.05m, junction1~junction26,
  강조구간) → connector405(2.97m)+connector404(9.89m, 둘다
  junction26 — 405로 진입해 404를 역방향으로 빠져나가는 경로.
  road299/318이 junction11↔junction26 왕복 사실상 동일 도로쌍이라
  기하학적으로 거의 같은 경로를 반대편(road318 전체 경유,
  connector358)으로 잡아도 539.74m로 사실상 동일 — 교차검증됨
  → road318(332.29m)+connector358(9.89m)) → road299(332.30m,
  junction26~junction11)
- 순수 "일반road" 기준으로는 **300 / 319 / 299** 3개(예전
  강조구간의 319·299가 실제로도 핵심 경로임을 재확인)
- 주의(모델링 단순화): 이 탐색은 차선(lane) 방향성을 반영하지
  않은 road-레벨 무방향 그래프 결과 — 실제 주행 가능 방향(일방
  통행 등)은 lane 정보로 별도 확인 필요. 경로 존재 자체(끊김
  없음)는 신뢰할 수 있으나 "이 방향으로 주행 가능"까지 보장하지
  않음
- **사용자 지시로 추가 기록**: 경로 존재는 확인됐으나 lane
  방향성 미반영. 일방통행·차선 방향으로 실제 주행 가능 여부는
  별개. OSM에 oneway 태그 62건 존재. CARLA 주행 시 확인 항목.
