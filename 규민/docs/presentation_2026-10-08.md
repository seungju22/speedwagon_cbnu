# 10/8 계획 발표 설명 자료 (맵 파트, 작성 2026-09-30 세션19)

이 문서는 숫자와 설명만 모은 것이다. 발표 대본이 아니다. 대본은 발표자가 직접 쓴다.
모든 항목은 네 가지를 갖춘다: 무엇을 했나 / 왜 그렇게 했나 / 결과 숫자 / 예상 질문과 답.
출처는 각 항목 끝 괄호(세션 보고서, 로그 파일).

## 0. 용어 (처음 나오는 순서대로)
- OSM: OpenStreetMap. 누구나 편집하는 공개 지도. 캠퍼스 도로 선(way)과 건물 외곽선을 여기서 가져왔다
- way: OSM 의 선 하나(도로 한 구간). highway 태그로 종류를 적는다(unclassified, service 등)
- xodr(OpenDRIVE): 자율주행 시뮬레이터가 읽는 도로 지도 형식. OSM 을 CARLA 변환기로 바꿔 만든다
- road / junction / 커넥터: xodr 의 도로 한 조각 / 교차로 / 교차로 안에서 들어오는 도로와 나가는 도로를 잇는 짧은 도로
- 반쪽 도로(half-road): 이 지도는 양방향 길 하나를 "한 방향 차선 1개 + 인도" road 두 개로 나눠 만든다.
  두 road 는 가운데 선(기준선)을 공유하고 방향만 반대다. 기준선 = 각 road 차선의 왼쪽 끝 = 실제로는 중앙선
- 기준선(reference line): xodr 에서 차선 위치를 재는 기준 선. 이 지도에서는 곧 중앙선
- paramPoly3: xodr 이 곡선 도로 모양을 적는 방식(3차 다항식 곡선). 조각과 조각 사이 이음매에서 곡률이 튀는 성질이 있다
- R2: 2m 구간 평균으로 잰 커브 반경(세션11 정의). 이음매에서 튀는 순간 곡률 대신 쓰는 값. 작을수록 급한 커브
- 평균R: road 길이 / 회전 각도(라디안). 커브 전체의 평균적인 반경
- TM(Traffic Manager): CARLA 기본 자동 주행 기능. 경로점만 주면 갈림길은 스스로 고른다
- BasicAgent: CARLA 가 제공하는 경로 추종 제어기. 준 경로점을 순서대로 따라간다(갈림길을 스스로 고르지 않음)
- GRP(GlobalRoutePlanner): CARLA 의 최단 경로 탐색 도구. 경로 후보를 뽑을 때 썼다
- 동기 20Hz: 시뮬레이터 시간을 0.05초씩 우리가 직접 한 칸(tick)씩 넘기는 방식
- tick: 시뮬레이션 한 칸 = 0.05초
- lat(횡편차): 차 중심이 차선 중심선에서 옆으로 벗어난 거리. + = 오른쪽(인도 쪽), - = 왼쪽(중앙선 쪽). 차선 반폭 1.675m

## 2. 대표 사례: 1m 벽 문제를 어떻게 좁혔나

### 2-1. 반쪽 도로가 무슨 뜻인가 (그림 설명용 구조)
- 그림 A(평면도): 실제 양방향 길 하나를 그린다. 가운데 중앙선, 양쪽에 차선 하나씩, 바깥에 인도
- 그림 B(지도 속 모습): 같은 길을 두 장으로 쪼갠다
  - road1247: 기준선(= 중앙선) 오른쪽에 차선 3.35m + 인도 2.80m. 왼쪽은 아무것도 없음
  - road1120: 같은 기준선을 공유하고 방향만 반대. 역시 오른쪽에 차선 + 인도
  - 두 road 가 기준선 위에서 등을 맞대고 붙어 있다(기준선 이격 0.000m, 방향 차 180°)
- 이 지도 plain road 260개 중 240개가 이런 쌍이다(세션11)

### 2-2. 그래서 벽이 왜 중앙선 위에 서나
- CARLA 는 지도를 불러올 때 도로 "가장 바깥 차선의 가장자리"에 높이 1m 벽을 자동으로 세운다. 차가 도로 메시 밖으로 떨어지지 않게 하는 안전 장치다
- 한 road 의 가장 바깥 차선은 "오른쪽 끝(인도 바깥)" 과 "왼쪽 끝" 두 곳이다
- 반쪽 도로는 왼쪽에 차선이 없으므로 "왼쪽 끝" = 기준선 = 중앙선. 그래서 왼쪽 벽이 중앙선 위에 선다
- 쌍둥이 road 도 같은 선에 자기 벽을 세운다 -> 양방향 길 한가운데에 1m 벽
- 그림 C(단면도): 인도 | 차선 | [1m 벽] | 차선 | 인도
- 커브에서 차가 조금만 중앙선 쪽으로 붙어도 벽에 걸린다

### 2-3. 어떻게 확인했나 (세 가지 독립 증거)
1. 소스 대조: CARLA 0.9.15 공식 GitHub 소스(MeshFactory.cpp 등)에서 벽 생성 규칙 확인.
   junction 이 아닌 road 에만, 가장 오른쪽 차선의 오른쪽 가장자리와 가장 왼쪽 차선의 왼쪽 가장자리에, 높이 벡터 (0,0,wall_height) 만 더한 수직면
2. 스크린샷 높이: 세션12 정지 지점을 위·옆에서 촬영(figures/16, 17). 도로 가장자리에 수직 판이 보이고 높이 추정 0.94~1.08m = 1m
3. 충격량 방향: 세션12 충돌 2,139건 중 2,138건이 차를 왼쪽으로 밀었고, 위아래 성분은 최대 0.65(크기 대비 0.008) = 수평으로 미는 수직면.
   소스 규칙대로 벽 선을 다시 그려 보니 중앙선 벽 끝(road1240 끝)이 첫 충돌 순간 차 앞쪽 bbox 안에 0.25m 들어와 있었다
- 그리고 세션10 의 92m 정지도 차 왼쪽 모서리가 기준선을 0.19m 넘은 뒤였다 -> 같은 벽이었을 가능성이 높다(추정, 직접 증명은 안 함)

### 2-4. 같은 xodr 로 벽만 켜고 끄는 대조 실험이 왜 가능했나
- 벽은 xodr 파일 안에 없다(xodr 안 "wall" 문자열 0건). 서버가 지도를 불러올 때 파라미터(OpendriveGenerationParameters.wall_height)로 만든다
- 그래서 지도 파일은 그대로(sha256 bf835cdfad0cea65) 두고 불러오는 명령만 바꿔 벽 1m / 0m 를 비교할 수 있다. 다른 변수는 하나도 안 바뀐다
- 벽을 끈 것도 사진으로 확인: 같은 카메라 위치에서 수직 판이 사라짐(figures/18, 19)

### 2-5. 결과

- 주행 거리: 548m 에서 막히던 곳 통과, 이후 도서관 경로 완주(궤적 774.4m [세션26-B])

## 3. 기각된 가설 (무엇을 의심했고 어떤 데이터로 버렸나)
1. GTT 미반환 (메모리): "CARLA 를 끄면 그래픽 메모리(GTT)를 돌려주지 않아 여유 메모리가 안 돌아온다" ->
   종료 후 GTT 2.89 -> 0.10GiB 로 돌아왔는데도 여유 메모리는 회복 안 됨. 대신 CARLA 자신이 swap 으로 밀렸고 Firefox 가 1.53GiB 를 쓰고 있었다 (세션17)
2. 기준선 오염 (메모리, 세션17) — 가설은 기각됐지만 그 과정에서 진짜 원인이 드러난 사례
   - 의심한 것: "서버 종료 후 약 3.7GiB 미회수" 계산의 기준선 9.3GiB 는 서버 실행 8분 전에 잰 값이었다. 그 사이 CARLA 와 무관한
     프로세스가 먹은 메모리까지 CARLA 누수로 계산됐을 것이다. 유력 용의자는 Claude Code 자신(대화가 길어질수록 RSS 증가)
   - 기각 근거(실측 2개): (1) 서버 기동 11초 뒤 CARLA RSS 3.97GiB -> 9.3 에서 5.4 로 줄어든 3.9GiB 는 CARLA 하나로 설명된다
     (2) Claude Code 자신의 PSS 0.31GiB(출처 setup_log 세션17 은 PSS [세션26-B]) -> 오염 요인이 되기엔 너무 작다
   - 기각 방식의 특이점: 가설의 방향은 맞았다. 측정은 실제로 오염돼 있었다. 틀린 것은 지목한 프로세스와 시점이다.
     진범은 Firefox 였고, 오염된 것은 기준선이 아니라 종료 후 측정값이었다. Firefox 가 CARLA 종료 7초 뒤에 떠서
     시점4 측정 57초 전부터 메모리를 먹었다(PSS 1.53GiB)
   - 결과: 3.7GiB 는 축소됐지만 사라지지 않았다. 최종 상태 "원인 일부 규명, 잔여 약 2GiB 미확인"(재부팅으로 회피)

3. 회복 거리: "중문 경로는 급커브 뒤 직선이 6.7m 뿐이라 자세를 회복 못 했다" -> 궤적을 보면 차는 그 직선(road1283)에 닿기 전에

## 4. 설계 결정과 근거

### 측위: NDT 대신 시뮬레이터 참값
- 무엇: 차 위치는 CARLA 가 아는 정답 위치를 그대로 쓴다
- 왜: 지도가 완전히 평평하고(elevation 878개 전부 0) 연석뿐이다. NDT 는 주변 모양을 맞춰 위치를 찾는데,
  평평한 직선 구간에서는 앞뒤로 미끄러져도 점수가 같아 앞뒤 위치를 못 잡을 수 있다(이론, 미검증).
  이번 평가 대상은 경로 계획·제어이므로 측위 오차를 섞지 않으려고 고정했다
- 숫자: 직선 road1172 119m, road1240 150m 같은 구간이 위험 후보
- 예상 질문: "실제 차에는 정답 위치가 없는데?" -> 맞다. 측위는 건물·기둥을 배치한 뒤 별도 실험으로 분리한다(pointcloud_design_draft.md)

### 벽 끄기 (wall_height 0)
- 무엇 / 왜: 2절. 반쪽 도로 구조 때문에 안전 벽이 중앙선에 선다
- 숫자: 충돌 1,604 / 2,139건 -> 0
- 예상 질문: "벽이 안전 장치라면 끄면 위험하지 않나?" -> 도로 밖 낙하를 대신 "메시 밖" 판정으로 잡는다. 중앙선 벽만 끄는 파라미터는 없다

### 동기 20Hz
- 무엇: 시뮬레이터 시간을 0.05초씩 스크립트가 직접 넘긴다
- 왜: (1) BasicAgent 의 PID 제어기는 한 칸이 0.05초라고 가정한다. 비동기로 돌리면 약 251Hz 로 돌아 적분·미분 항이 약 12배 틀어진다.
  (2) 비동기는 실행마다 프레임 간격이 달라 같은 시나리오가 다른 결과를 낸다
- 숫자: 같은 경로 두 번 주행 시간 차 0.3s(6 tick), 커브 이탈량 차 0.05m 이하(세션17)
- 예상 질문: "실시간이 아니지 않나?" -> 맞다. 대신 재현성이 생긴다. 시간은 시뮬 시간으로 잰다

### BasicAgent (TM 대신)
- 무엇: 경로점을 순서대로 따라가는 제어기
- 왜: TM 은 갈림길에서 경로점과 가까운 커넥터를 스스로 고른다. 반쪽 도로 구조라 교차로마다 U턴 커넥터가 계획 커넥터와 겹쳐 있어
  세션13 에서 TM 이 직진 대신 U턴 커넥터(r1697)를 골라 인도로 올라갔다. 셔틀은 정해진 노선이라 갈림길을 스스로 고를 필요가 없다
- 숫자: 세션13 TM 은 U턴 커넥터 r1697 에 진입해 인도로 올라감. 나머지 3곳(r1915 0.12s, r1449 0.16s, r1429 0.58s)은 위치 조회로 커넥터 위가 잠깐 기록된 것이며 커넥터 겹침 오탐일 수 있다(세션15). BasicAgent 전환 뒤 U턴 진입 0 [세션26-B]
- 예상 질문: "경로계획 오픈소스는 왜 안 쓰나?" -> 정류장 5곳이라 경로를 미리 고정한다(회의 결정). 대신 경로는 방향 그래프로 뽑아 검증한다

## 5. 예상 질문과 답 (사실과 다음 계획)
1. 왜 실제 건물이 없나
   - 사실: 지금 지도는 OSM 도로만 변환한 것이다. 건물은 소품(prop) 배치 시험만 해 봤다(세션15, 나무·건물 배치 성공)
   - 다음: 발표 후 CARLA 기본 건물 에셋 중 비슷한 것을 골라 캠퍼스를 알아볼 수 있게 배치(회의 결정). NDT 측위 실험에도 필요
2. 왜 정차점이 문에서 46m 떨어져 있나
   - 사실: 북문 정차점은 도서관 건물에서 가장 가까운 "차가 다닐 수 있는 도로" 위 점이다. 그보다 가까운 도로가 지도에도 실제로도 없다.
     양성재도 45.7m 로 같은 수준. 남문은 26.1m
   - 다음: 건물 출입구 좌표를 실측하면 도보 거리를 출입구 기준으로 다시 잰다
3. 중문은 왜 실패했었나 (세션20 완주)
   - 사실: 중문 가는 길의 좌회전 r1592 가 반경 7.8m 로 지금까지 통과한 어떤 커브(9.0m 이상)보다 급하다.
     세션18 에서 차가 커브 안쪽으로 파고들어 중앙선을 차 중심 기준 0.23m 넘었고, 옛 규칙이 이를 즉시 실패로 처리했다. 충돌은 0
   - 세션20: 판정 기준만 "깊이 0.5m·지속 1s" 로 바꿔 재주행 -> 완주. 이탈은 그대로 있다(차체 1.19m, 중심 0.29m, 2.9s) = 지표로 남김
   - 예상 질문 "기준을 느슨하게 해서 통과시킨 것 아닌가?" -> 그렇다, 그래서 이탈량을 지표로 따로 잰다. 기준은 "멈춰야 할 위험"(마주 오는 차 자리에 차 중심이 깊이·오래)만 잡는다
   - 다음: 급커브 감속(--sharp-speed), 한 번에 하나씩
4. 후문은 왜 못 가나
   - 사실: 후문 쪽 길이 [세션26-B] OSM 에서 "주차장 통로(service)" 로 표시돼 변환에서 빠졌다. 지금 지도에서 가장 가까운 도로는 후문에서 217m
   - 다음: 미변환 구간은 2026-10-04 현장 조사 결과를 반영해 재변환 대상을 확정하는 중이다. 후문 구간은 추가 조사 후 결정한다 [세션26-B]. 시험 변환에서 후문 경계 1.2m 앞까지 도달 확인(주행은 미실시)
5. 이 맵이 실제 캠퍼스와 얼마나 같나
   - 사실: 도로 선의 위치는 OSM 좌표 그대로(투영 검산 90점 중앙값 1.25m). 차선 폭은 변환기 기본 3.35m, 도로 높낮이 없음(완전 평면.
     예: 양성재 가는 길은 정문 우회전 뒤부터 오르막인데 반영 안 됨, OSM 에 높이 정보가 없음),
     건물 없음. 캠퍼스 도로 중 변환 대상 73개 way 만 들어 있다. 정문은 들어오는 길만 있고 나가는 길이 빠져 있다(재변환 때 추가)
   - 높이 0 한계(숨기지 않음): OSM 에 고도 정보가 없어 맵 전체가 z=0. 양성재는 실제로 오르막인데 평지로 계산됐다.
     제동 거리와 주행 시간이 모두 평지 가정이고, 내리막에서는 정지거리가 길어진다(감속도가 g·sinθ 만큼 줄어듦)
   - 해결 경로(약속 아님): OpenDRIVE 는 elevationProfile 을 지원한다. 국토지리정보원 DEM 또는 SRTM 에서 고도를 가져와 넣을 수 있다.
     작업량이 작지 않아 중간 발표 이후 과제
   - 다음: 재변환 후 실제 사진·항공사진과 대조, 건물 배치
6. 성공률은 어떤가
