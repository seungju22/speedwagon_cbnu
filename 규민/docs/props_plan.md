## 3-2. OSM 건물 폴리곤 추출 (완료)

스크립트 map/scripts/s22_buildings.py (신규, 읽기전용, 서버 불필요)
- 입력: 원본 OSM(data/raw/cbnu_campus.osm), 대상 xodr(기본 frozen_v1)
- 건물: building 태그 + name 이 있는 way. 기본은 주요 건물 이름 목록, --all 이면 이름 있는 건물 187개 전부
- 좌표 사슬: 폴리곤 면적 중심(위경도) -> 지역 TM -> xodr(= TM + offset) -> CARLA(x, −y)
  - 투영 중심 lat_0/lon_0 와 offset 은 실행할 때마다 xodr 머리말에서 읽는다. 숫자를 코드에 박지 않는다
  - 머리말에 lat_0/lon_0 이 없으면(세션3 문제 상태) 중단한다
  - 재변환 뒤에는 --xodr 새파일 만 주면 된다. center_map 이동량(offset)이 바뀌어도 자동 반영
- 자기 검사: xodr junction 이름 = OSM 노드 id. 노드를 같은 사슬로 투영한 위치와 그 junction 커넥터 시작점 평균의 거리 중앙값.
  frozen_v1: 90개 junction, 중앙값 3.35m(커넥터 시작점이 교차점에서 차선 폭만큼 떨어져 있어 생기는 값. 세션4 정합 잔차 3.7m 와 같은 수준)
- 출력 CSV map/data/processed/s22_buildings.csv: 이름, way id, 중심 위경도, CARLA x·y, 면적, 최소 외접 사각형 길이·폭·방향(CARLA yaw),

## 3-3. 배치 스크립트 설계 — map/scripts/place_props.py

목적: 건물 자리에 대용 소품을 놓아 화면에서 캠퍼스를 알아볼 수 있게 한다. 주행 실험 때는 끈다

입력
- 건물 목록: s22_buildings.csv 의 이름·중심 위경도·폴리곤 길이·폭·방향 (CARLA x·y 열은 참고용. 배치할 때는 위경도에서 다시 변환)
- 배치 설정(스크립트 안 표 또는 --config JSON): 건물 이름 -> 소품 종류(registered 이름 또는 mesh_path), scale, 방향 보정, 개수
- 맵: 서버가 지금 불러온 지도(world.get_map().to_opendrive()). 그 머리말로 좌표를 변환하고 sha256 앞 16자를 로그 첫 줄에 찍는다
  -> CSV 를 만든 맵과 서버 맵이 달라도(재변환 후) 위경도에서 다시 계산하므로 맞는다

명령 형태
- --dry-run: 서버 맵으로 좌표·도로 침범 검사만 하고 결과 출력(소환 안 함)
- --apply: 검사를 통과한 것만 소환. 소환한 actor id 를 상태 파일(map/docs/logs/props_state.json)에 기록
- --clear: 상태 파일의 actor 를 지우고, 남은 static.prop.mesh·우리가 소환한 종류도 지운다. 지운 개수 출력
- --draw: 디버그 상자·이름만 그린다(3-4). 소환과 별개
- --only NAME: 특정 건물만(시험 배치용)

도로·차선 침범 검사 (배치물이 주행을 막으면 안 된다)
- 발자국(footprint) = 소품을 놓을 사각형. 소환 전에 알 수 없어서 설정값(길이·폭)으로 둔다.
  actor bounding_box 는 믿지 않는다(세션15 House02 bbox 0.33m 인데 실제는 집 한 채)
- 검사점: 사각형 네 모서리 + 둘레 1m 간격 + 중심
- 규칙 1 (겹침 금지): 각 검사점에서 map.get_waypoint(위치, project_to_road=False, lane_type=Driving|Sidewalk|Shoulder|Parking)
  가 차선을 돌려주면 그 점은 도로 위 -> 그 소품은 배치 안 함
- 규칙 2 (여유): 각 검사점에서 project_to_road=True 로 가장 가까운 주행 차선 중심까지 거리 − 차선 반폭 >= 여유(기본 3.0m).
  여유 3m 근거: 인도 2.80m 를 넘어서는 자리 = 인도 바깥
- 규칙 3 (경로): 정류장 루트 4개(test_drive.py ROUTES)의 계획점 polyline 에서 차체 반폭 0.9m + 여유 3m 안에 들어오면 배치 안 함
- 규칙 4 (정류장): 정차점 반경 10m 안 금지(촬영·승하차 자리)
- 실패하면 대안 위치를 찾는다: 폴리곤 중심에서 도로 반대쪽으로 1m 씩 최대 20m 이동하며 재검사. 그래도 안 되면 건너뛰고 이유 출력
- 소환 직후 확인: 소품마다 get_location() 이 의도 위치와 0.5m 안인지, 소환 실패(None) 개수

켜고 끄기
- 기본은 꺼짐: 주행 스크립트(test_drive.py)는 소품을 만들지 않는다. 소품은 place_props.py --apply 를 따로 실행해야만 생긴다
- 주행 실험 전 확인 절차: place_props.py --clear 후 world.get_actors().filter("static.prop.*") 0개를 확인하고 주행
- 소품은 서버 재시작이나 load_world/generate_opendrive_world 때 사라진다(지도를 새로 만들면 actor 가 지워짐)
- 영상 촬영용 실행과 지표 측정용 실행을 섞지 않는다. 소품을 켠 주행은 지표에 넣지 않는다(변수 분리)

메모리
- 소환 전·후 free 와 gtt_used 를 찍는다. 세션15 5개는 변화 거의 없음(avail 4.5 -> 4.4Gi, gtt 1.53 -> 1.52)
- 대량 배치(수십~수백 개)는 측정한 적 없다. 늘릴 때는 10개 단위로 늘리며 잰다. 중단 기준(avail < 2GiB, swap > 4GiB)은 그대로

## 3-4. 디버그 표시 대안 — world.debug

방법
- world.debug.draw_box(carla.BoundingBox(중심, 반크기), 회전, 두께, 색, life_time)
- world.debug.draw_string(위치, "중앙도서관 구관 (N12)", 색, life_time)
- 위치와 크기는 3-2 의 폴리곤 중심·외접 사각형을 그대로 쓴다. 건물 하나에 상자 1개 + 이름 1개
- life_time 은 초 단위. 0 이면 영구라 지울 수 없다 -> 녹화 길이에 맞춰 유한값(예 300s)으로 그리고 필요하면 다시 그린다

장점
- 즉시 가능, 에셋 고를 필요 없음, 위치가 OSM 폴리곤 그대로라 정확함, 이름이 화면에 뜬다
- 물리 충돌체가 없다. 주행을 절대 막지 않는다 -> 주행 영상 위에 겹쳐도 지표에 영향 없음

단점
- [정정, 세션22 Phase 4 실측] "카메라 센서 영상에는 안 잡힌다" 는 지시문 전제는 틀렸다.
  draw_box(두께 0.5, life_time 600s)를 그린 뒤 sensor.camera.rgb 1280x720 으로 찍은 영상에 상자 선이 그대로 찍혔고,
  선 주변 빛 번짐(분홍)이 화면 대부분을 물들였다(figures/24, 25~27). 이름 글자(draw_string)는 이 사진들에서는 보이지 않았다
  -> 디버그 표시를 켠 채 카메라 영상을 쓰면 인지 입력이 오염된다. 카메라 실험 때는 반드시 끄고(수명 만료 대기), 수명은 짧게 준다
  -> 한 번 그린 것은 지우는 API 가 없다. 수명이 끝날 때까지 남는다(이번 600s)
- 물리 형상이 없으므로 LiDAR 점군에는 나오지 않을 것으로 본다(미확인. 광선 대상 충돌체가 없음)
- 그래서 NDT 측위 실험(점군 정합)에는 쓸모가 없다

용도 구분
- 발표 영상·설명 그림: 디버그 상자 + 이름 (정확한 위치, 즉시, 주행 무영향). 단 카메라 센서를 쓰는 실험과 같은 시간대에 그리지 않는다
- 보기 좋은 화면(캠퍼스 느낌): 정적 메시 건물·나무 소품 (모양은 대용품)
- 센서·인지·측위 실험(LiDAR 점군, 카메라, NDT): 정적 메시 소품만 의미가 있다. 이때는 소품 배치가 실험 조건의 일부가 되므로
  배치 목록과 맵 sha256 을 로그에 남긴다
- 주행 지표 측정: 아무것도 놓지 않는다
